# 视频实测复盘库

> 用途：沉淀“真实模型已经测出来”的经验，不写空泛理论。
> 说明：本库服务于 `~plan` 与 `~prompt`。遇到相似戏点时，先查这里的成功条件、失败条件与修正方向，再决定拍法与 prompt。

---

## 一、使用规则

1. 这里只记录已经经过真实视频测试验证过的结论。
2. 每条经验至少写清：
   - 适用场景
   - 已验证有效的做法
   - 已验证高风险或失败的做法
   - 对 planner / storyboard 的直接影响
3. 本库优先级高于“临场想当然”：
   - 如果理论上可行，但实测已经反复翻车，默认以实测结论为准
4. 本库不是单集提示词归档：
   - 不直接堆历史 prompt 原文
   - 只沉淀可复用的规则、模式判断和修正方向

## 二、已验证经验

### 0. 分镜图驱动容易退化成幻灯片

- 适用场景：
  - 适用模式：`modes/storyboard_frame_mode.md`
  - 使用 2~4 张分镜图生成同一段视频
  - 关键帧之间是不同构图、不同景别或不同人物组合
  - 群像分工、对话压场、职责落点等“关系变化”戏点
- 已验证有效：
  - 把关键帧写成构图锚点，而不是时间停留清单
  - 只上传成品分镜图、不再上传单独角色图时，必须在直贴 prompt 开头补 `图内人物指认`，用“角色名 = 图中可见外貌特征 + 画面位置/职责”绑定身份
  - 每个关键帧节点都写清“谁先动、身体怎么动、道具/站位怎么变、最后落到什么关系”
  - 明确要求连续视频动作，不要把参考图当作静态画面依次播放
  - 构图差异很大时，写成 multi-shot coverage，并保证每个镜头内部都有可见动作
  - Beat04 实测：补充 `图内人物指认 + multi-shot coverage + 动作桥检查` 后，人物动作明显增强，不再只是静态切图
- 已验证失败：
  - “前 3 秒从 @图片1 开始，中间 3 秒推进到 @图片2，最后 2 秒过渡到 @图片3”
  - 只写“自然过渡 / 顺着推进 / 落到关系”，没有动作主语和动作桥
  - 只写老三、老烟头、老二、大胡子等角色名，但没有说明这些名字分别对应分镜图里的谁
  - 继续增加“电影感、压迫、紧张”等形容词，人物仍只会眨眼、轻微呼吸或被镜头轻推
- 对 planner / storyboard 的直接影响：
  - `seedance_storyboard_prompts.md` 在分镜图驱动时必须新增 `图内人物指认`
  - `seedance_storyboard_prompts.md` 必须新增 `动作桥检查`
  - `关键帧时间分配` 只写镜头功能，不写静态停留时长
  - 如果一次测试已经像 PPT，下一版优先重写动作桥；仍不动时切换到首尾帧、行为起始帧或拆条生成

### 1. 关键叙事物必须 `@`

- 适用场景：
  - 适用模式：优先 `modes/omnipotent_mode.md`；分镜图模式仅在关键物已经进入成品分镜图时不额外上传
  - 关键道具揭示
  - 情感重击镜
  - 线索发现镜
  - insert / reveal / insert + reaction 结构
- 已验证有效：
  - 只要“这个物不出现，戏就不成立”，该物就必须单独作为参考图上传并在正文中 `对象名@图片X`
  - 人物、场景、关键物三者各自承担不同信息职责时，三者都应明确引用
- 已验证失败：
  - 只 `@人物` 和 `@场景`，不 `@关键物`，模型容易把关键物替换成洞口、土坑、普通地面异常或其他安全物
- 对 planner / storyboard 的直接影响：
  - `information_anchor` 落在“物”时，`registry 素材引用` 与 `本次上传顺序` 中必须包含该物

### 2. 敏感异物语义会被模型主动改写

- 适用场景：
  - 适用模式：全模式通用，尤其影响 `modes/omnipotent_mode.md` 与分镜图前置生图
  - 遗落肢体
  - 明显残缺人体部位
  - 高风控惊悚细节
- 已验证有效：
  - 如果戏点允许替换，优先改写为“关键旧物”“身份指向物”“异常遗落物”等更安全的线索物
  - 如果必须保留冲击点，优先把“物”的信息拆到静帧或前置生图环节，再让视频主打 reaction
- 已验证失败：
  - 直接让视频模型生成敏感肢体类线索物，容易被替换成坑口、洞口、重复物件或巨型异物
- 对 planner / storyboard 的直接影响：
  - 高风控物件默认提升风险等级
  - 优先考虑 `INSERT_REACTION` 或 `OBJECT_SHOCK_REACTION`

### 3. 4 秒状态镜不要硬撑，优先改成功能关系

- 适用场景：
  - 适用模式：公共决策层，先查 `generation_decision_library.md`
  - 观察
  - 等待
  - 倾听
  - 蹲守
  - 情感停顿
- 已验证有效：
  - 先设计“信息 -> 反应”“异常 -> 反应”“动作 -> 后果”
  - 在单次请求内使用 multi-shot 或 coverage 组织，让 4 秒里发生明确关系变化
- 已验证失败：
  - 让人物在 4 秒里只维持一种状态，容易发呆、动作极少、镜头只有轻推
- 对 planner / storyboard 的直接影响：
  - 状态型 beat 不得默认落成单镜头长观察镜
  - 必须先判断是否改写为 `INSERT_REACTION`、`POV_REACTION`、`OBS_TENSION`

### 4. 第一镜正面平铺容易变摆拍

- 适用场景：
  - 线索发现
  - 观察异常
  - 情感重击
  - 等待压迫
- 已验证有效：
  - 第一镜优先使用后侧三分之四、背侧观察、偏侧关系镜
  - 让人物像“被画面中的信息击中”，而不是“站给观众看”
- 已验证失败：
  - 正面中景或正面平视建立镜，容易变成展示图 / 摆拍
- 对 planner / storyboard 的直接影响：
  - 当第一镜的 `viewer_relation` 是“先看信息再看人”，默认禁止正面摆拍开场

### 5. 关键物应只占前景小面积

- 适用场景：
  - 关键旧物
  - 异常线索
  - insert + reaction 类镜头
- 已验证有效：
  - 关键物落在前景边缘或前景小面积区域
  - “它是戏点，但不是巨物”
- 已验证失败：
  - 关键物一旦占满前景，模型会把它拍成主角，反而压掉人物情绪
- 对 planner / storyboard 的直接影响：
  - `screen_geography` 和最终 prompt 都要显式限制尺寸与画面占比

### 6. 群像连续性不能写“延续上一拍”，必须写当前站位事实

- 适用场景：
  - 多人同框
  - 连续对话
  - 连续冲突
  - 群像反应
- 已验证有效：
  - 用 `screen_blocking_facts`、`axis_rule`、`camera_side_rule`、`dialogue_address`、`eyeline_rule` 把当前画面的左右关系、前后关系和交流对象写死
- 已验证失败：
  - 只写“延续上一拍”“保持一致”，全能模式不知道上一条视频是什么
- 对 planner / storyboard 的直接影响：
  - 连续群像戏默认必须输出 `固定屏幕站位事实`

### 7. 对话镜头必须写清“说给谁听”

- 适用场景：
  - 群像对话
  - 顶撞
  - 定性
  - 命令
- 已验证有效：
  - 写清说话对象、目光方向、身体朝向，以及其他人的异步反应
- 已验证失败：
  - 没写交流对象时，说话人容易对着镜头播报，其余角色变成整齐摆拍围观
- 对 planner / storyboard 的直接影响：
  - 带台词 beat 默认补齐 `dialogue_address`、`eyeline_rule`

### 8. 群像反应必须异步分配

- 适用场景：
  - 群像对话
  - 定性
  - 危险揭示
  - 等待压迫
- 已验证有效：
  - 主表演者承担完整动作 / 台词
  - 其他人各自只承担 1~2 个不同步的小反应，例如下颌收紧、视线压地、肩背绷住、手指收紧
- 已验证失败：
  - 只写主表演者，其余人会静止
  - 给所有配角同一种表情标签，会像复制粘贴
- 对 planner / storyboard 的直接影响：
  - 群像镜头必须显式分配“谁主演、谁反应、如何异步”

### 9. 洞口 / 黑暗威胁镜要把危险源藏住

- 适用场景：
  - 拉绳
  - 洞口压迫
  - 黑暗中未知存在
- 已验证有效：
  - 让绳索张力和人物受力承担戏，危险源留在黑暗里不可见
- 已验证失败：
  - 如果不写清“不要出现任何肢体 / 物体伸出”，模型容易在洞口边缘生成奇怪手臂或挂件
- 对 planner / storyboard 的直接影响：
  - `information_anchor` 在“不可见威胁”时，要优先写“只见力量，不见目标”

### 10. 已跑通模板：关键物情感重击镜

- 适用场景：
  - 角色忽然认出地上旧物
  - 看见身份线索后被击中
  - “先信息、后人物反应”的戏点
- 已验证有效结构：
  - `Shot 1`：后侧三分之四或背侧关系镜，先看地上的小型关键物，再看人物被钉住
  - `Shot 2`：沿同一信息方向收人物偏侧 reaction
  - 保持夜景 / 月光 / 冷色压迫氛围单独锁定
- 已验证失败结构：
  - 第一镜正面对物摆拍
  - 关键物过大
  - 不 `@关键物`
- 对 planner / storyboard 的直接影响：
  - 此类 beat 默认优先匹配 `OBJECT_SHOCK_REACTION`

### 11. 转向确认类戏点必须拆成“画外异动 -> 转向反应 -> 延迟揭示 -> 关系落点”

- 适用场景：
  - 背后异动
  - 角色转身确认
  - 暗处目标显现
  - 先未知、后确认的危险揭示
- 已验证有效：
  - 先把 setup 空间与 reveal 空间分开：第一镜只交代角色原本面朝的空间，危险所在区域保持画外
  - 反应镜不只负责表情，还要完成注意力和身体朝向的空间转向
  - 揭示镜再第一次进入危险所在区域，只让目标部分成立，不做完整展示
  - 最后一镜尽量落在人与危险的关系成立，而不是只停在“目标露脸”
- 已验证失败：
  - 虽然写了 `Shot 1 / Shot 2`，但每镜没有明确功能，只是同一画面看清楚一点
  - setup 镜和 reveal 镜共享同一树位 / 同一空间锚点，导致转身没有意义
  - 第一镜提前露出揭示区、红色肢体、目标轮廓，悬疑被提前泄掉
  - 最后一镜让目标完整站出来，变成展示而不是对峙
- 对 planner / storyboard 的直接影响：
  - 此类 beat 不能只写默认镜头数，必须明确 `shot_function_chain`
  - `shot_function_chain` 默认优先考虑：`异动建立 -> 反应转向 -> 延迟揭示 -> 关系回扣`
  - `screen_blocking_facts` 必须显式区分 setup 区与 reveal 区，不得让两者共享同一主锚点
  - 最终 prompt 必须避免 setup 镜提前出现 reveal 区

### 12. Beat04 全能模式：群像分工容易干净但发死

- 适用场景：
  - 适用模式：`modes/omnipotent_mode.md`
  - 多角色 + 场景 + 道具多图引用
  - 分工、命令、职责落位、洞口队列等群像关系戏
- 已验证有效：
  - 多图 `@` 能明显稳定人物身份、场景和关键道具
  - 当前站位事实、轴线、谁对谁说、谁守什么职责必须写清
  - 关系型 Beat 要用 `MASTER_COVERAGE / PRESSURE_DIALOGUE`，并把动作桥转译成可见节点
- 已验证失败或高风险：
  - 为了保住四人全在画面里，整段容易变成多人全身摆拍
  - “同侧全景 + 轻推 + 点名”会让视频干净但缺乏表演动势
  - 只让老烟头动作，其他人容易变成站位背景
- 对 planner / storyboard 的直接影响：
  - 群像 master 只负责建立关系，后续必须至少有一镜转向手、侧脸、局部道具、过肩压力或反应近景
  - 技法推理中必须新增 `emotional_camera_reason`，说明为什么用当前景别表达当前人物心理
  - 若一个 Beat 的最终 prompt 从头到尾都是多人全身关系说明，视为未完成影视化调度

### 13. Beat04 下洞机制：深洞不能靠“扶洞沿”成立

- 适用场景：
  - 适用模式：全模式通用，尤其影响 `modes/omnipotent_mode.md`
  - 竖井式盗洞、下水道入口、深洞下行、绳降、洞壁移动
- 已验证有效：
  - 先让地面控绳者在第一帧成立，再让下行者开始下降
  - 下行动作写成绳降 / 贴壁下沉 / 脚找支点 / 手抓绳受力
  - 用高俯角或侧向机制镜看清洞口、绳线、队列和守绳关系
  - 如入口下行动作连续失败，单独拆出 `MECHANISM_CUTAWAY` 或侧剖面 Beat
- 已验证失败或高风险：
  - 第一帧没有老三拉住/控制尾绳，后续职责会显得突兀
  - 深洞下行只写“手扶洞沿”不可信，模型会拍成浅坑、台阶或轻松钻洞
  - 同一 Beat 既要地面队列、三人下行、老三守绳、洞内动作，容易互相稀释
- 对 planner / storyboard 的直接影响：
  - 深洞下行默认命中 `VERTICAL_DESCENT_MECHANISM`
  - 第一镜必须包含地面控绳职责，或明确将控绳职责拆到上一 Beat 的结束帧并在本 Beat 第一帧继承
  - 下洞过程如仍不稳，优先拆 Beat：`地面控绳/入口起手` -> `侧剖面/洞壁下降机制` -> `地面等待`

## 三、当前已验证可复用结论

- 全能模式下，连续性靠“当前请求中的显式 screen geography”，不靠模型记忆上一条视频
- `Shot 1 / Shot 2` 不是目的，功能关系才是目的
- 这套工作流的正确迭代方式是：
  - 先产出
  - 再实测
  - 再把有效/失败经验沉到本库
  - 再由 `~plan` / `~prompt` 反向调用
